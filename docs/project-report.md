# 結合歷史交易案例檢索與對話式風險提示的黃金交易輔助平台

專題報告 第一版

## 一 摘要

本專題建置一個黃金交易輔助平台，讓具有交易經驗的使用者在首筆進場或加倉前，同時查看行情、目前持倉、相似歷史操作與新增部位的風險。使用者可在券商式表單輸入訂單，也可透過中文對話提出交易意圖。系統先形成待確認草稿，由程式完成案例檢索與價格情境試算，再顯示風險說明；使用者核對後才能確認操作。

本專題的核心價值，是把分散在行情視窗、交易紀錄與心算中的資訊集中到同一個下單前流程。歷史虧損案例能提醒使用者曾出現的操作結果，部位試算則回答「這次再加多少手，若價格繼續不利，整體損失會變多少」。案例是可追溯的參考，不是新訂單的勝率預測，也不把原交易員的每次操作當作標準答案。

第一版採 React 與 TypeScript 製作前端，FastAPI 製作後端，以 Decimal 計算價格、手數及損益。已建立本機回放、首筆與加倉草稿、案例檢索、風險確認、持倉及平倉流程；券商模擬模式目前顯示未連線並阻止送單。中文助手可使用本地規則解析，另保留需明確啟用的外部語言模型解釋介面。現階段未使用外部模型金鑰驗證，也未完成實際券商 API 串接。後續依資料品質與整合驗證，逐步增加掛單、K 線形狀、途中高風險案例、持倉警示與多使用者模擬帳戶授權。

關鍵字：黃金交易、歷史案例檢索、下單前風險、對話式介面、歷史回放。

## 二 背景與問題

黃金交易常以槓桿及多筆訂單進行。即使單筆手數看似不大，連續加倉仍可能使整體部位快速增加。當使用者只注意平均進場價改善，容易忽略同方向曝險同步擴大。平台因此需要呈現加倉前後的總手數與價格情境，而不能只顯示新增訂單的停損金額。

另一方面，交易紀錄通常適合事後查看，使用者準備下一筆訂單時，未必能快速找出過去相近操作。只以最終盈虧排序也會混淆「當時條件相近」與「事後結果相近」。本專題先以方向、首筆或加倉、手數及可見持倉條件形成匹配池，再呈現其結果分布與案例。歷史結果用來說明參考案例，不進入相似度排序。

對話助手可降低查找與輸入成本，但數字計算與交易確認需要清楚邊界。使用者說「買進黃金 0.1 手」時，助手只能準備草稿，不能直接送出。若停損未設定、案例不足、行情未連線或資料時區未知，系統必須明示限制，不以流暢文字掩蓋資訊缺口。

現有資料包含 HTML 對帳單、Excel 與 CSV 操作紀錄，但部分 HTML 截斷、來源帳戶對應未確認、事件時間精度不足。這些限制使完整策略模仿與可靠勝率預測難以成立。因此，初版將驗收目標放在流程可用、計算正確、證據可追溯與限制可理解，正式機器學習訓練另待資料條件成熟後評估。

## 三 使用者與產品價值

平台主要服務已有交易經驗、會自行決定方向與手數的黃金交易使用者。團隊及教師可使用相同案例與回放時間重現操作，也可比較多人是否理解加倉後的風險變化。原交易員提供共享案例來源；產品能否讓多位使用者反覆使用，仍需後續任務測試驗證。

首筆進場時，平台提供同方向、相近手數的歷史候選，協助使用者查看來源及差異。加倉時，進一步比較既有可見訂單數與目前價格相對持倉均價的位置，並計算整體情境損失。兩種流程共用訂單草稿，但使用不同操作條件，避免把空手與已有部位混為同一情境。

本專題的特色是整合可解釋的案例與具體部位變化。系統回答的是「找到哪些參考」「哪些條件相同」「哪些條件尚未核實」「此草稿增加多少曝險」。是否提高決策品質、是否有長期使用與付費需求，都需要使用者研究，不能由功能展示直接推出。

## 四 資料來源與行為分群

### 資料處理原則

原始 HTML、Excel、CSV 與參考文件保持唯讀。解析後保留原始文字、商品代碼與來源列號，再新增正規化欄位；價格、金額及手數以 Decimal 處理。存提款與市場交易分開，非黃金商品保留並標記。帳戶識別資料、原始交易檔案、私人匯入案例及金鑰不納入公開 GitHub 交付，公開版本使用明示的合成示範資料。

黃金商品家族可在分析欄位統一辨識，但不覆蓋來源代碼。相同檔案副本與可能重複的交易列分別處理：檔案去重有檔案雜湊依據，交易列相似仍可能是合法拆單，因此只標記候選，不任意刪除。

### 可觀察的行為類型

分群先依可見訂單的時間重疊、方向、成交價與既有均價判斷。它描述紀錄中出現的操作形式，不推斷交易員心理、進場原因或完整策略。

| 類型 | 可觀察條件 | 主要解讀限制 |
|---|---|---|
| 可見初始單 | 當時沒有可見既有黃金持倉 | 缺漏紀錄可能藏有其他部位，不能證明空手 |
| 價格不利時同向加單 | 新單方向相同，價格相對既有均價不利 | 不等於拗單，也不證明加倉理由 |
| 價格有利時同向加單 | 新單方向相同，價格相對均價有利 | 不等於已辨識順勢策略 |
| 同價加單 | 同向新增單的價格與可見均價相同 | 密集拆單未必是多次獨立決策 |
| 反向或混合持倉 | 當時已有反向或雙向可見部位 | 帳戶的淨額或逐筆持倉模式需另核實 |
| 時間順序不明 | 同時間存在無法排序的開平倉事件 | 不強行重建事前持倉 |

### 下單前檢索與事後結果

初版採透明的條件距離，未訓練相似度模型。先依買賣方向與首筆或同向加倉分池，再比較手數；加倉候選可比較既有訂單數與價格相對均價的距離。價格及金額仍保留 Decimal，檢索距離是無單位的排序分數。每個候選操作群最多選一筆，減少同一組拆單重複佔據結果。

查詢時只能使用已可取得結果的歷史案例。案例須在查詢時點之前完成平倉；未知時區採保守可用時間界線，不能把這項處理稱為已確認時區。完整匹配池形成後，才優先顯示虧損案例，並同時揭露獲利、虧損、持平及未知結果數。其獲利比例只是歷史描述，不是目前新訂單的未來機率。

盤面相似度需要可信的時區映射與已收完 K 棒。目前歷史案例的市場對齊仍受限制，未核實的 K 線與市場特徵不進入排序，也不補零。案例細節沒有可信 OHLC 時，應顯示無法提供行情圖的原因；回放圖中的合成行情須與真實案例來源分別標示。

## 五 系統架構與分工

前端是可切換明暗的交易工作台，負責顯示 K 線、報價、表單、對話、案例與持倉。後端保存回放時鐘、訂單草稿與帳戶狀態，依 API 契約傳遞資料。財務值以十進位字串傳輸，避免前端浮點數重新計算損益；圖表座標才使用一般數值。

| 模組 | 程式負責的工作 | 語言模型的角色 |
|---|---|---|
| 行情與持倉 | 收棒時間、均線、報價、損益及帳戶版本 | 解釋已提供的數字與資料限制 |
| 訂單草稿 | 格式檢查、方向、手數、停損停利與狀態 | 協助表達意圖；目前草稿由本地解析建立 |
| 案例檢索 | 可用時間、候選篩選、距離與結果分布 | 用白話整理匹配原因與差異 |
| 風險檢查 | 加倉前後手數、均價及價格情境損益 | 說明風險，不能改寫數值或保證結果 |
| 操作確認 | 版本驗證、防重送、回放成交及平倉 | 沒有確認或送單的工具權限 |

本地助手能解析明確中文指令並描述行情。外部 LLM 僅在明確啟用且完成金鑰設定後使用必要摘要；摘要不包含完整對帳單、帳戶識別或來源檔名。外部服務錯誤時保留程式結果並顯示無法取得文字解釋。此介面目前未以實際金鑰完成驗證，不能稱為已驗收的 AI 服務。

初版後端是記憶體中的單一展示工作階段，適合可重現 Demo。它尚未具備正式多租戶隔離、長期資料保存與多人併發交易工作階段。後續增加登入與個別帳戶時，需要重新設計資料庫、權限、工作階段與事件紀錄。

## 六 券商式介面與操作流程

### 畫面配置

中央放置 5 分、15 分與 1 小時 K 線，可查看均線與區間高低點。右側以頁籤切換訂單表單與對話助手；下方顯示持倉、訂單歷史、相似案例及資料分群。工具列持續標示資料來源、回放時間、模式與連線狀態，讓使用者分辨本機回放與未連線券商模擬環境。

畫面採緊湊表格與清楚數字，首筆、加單與平倉在可見圖表範圍標記。送出草稿後開啟確認視窗，把本次方向、手數、停損停利、案例與風險放在一起。案例不足不阻斷風險試算，也不妨礙使用者在回放模式自行確認。

### 首筆進場

使用者查看回放行情後，在表單選擇 BUY 或 SELL、輸入手數，可選填停損與停利；也可輸入「買進黃金 0.1 手」。後端驗證數字有效性與停損停利方向，再保存含報價及帳戶版本的草稿。使用者閱讀首筆候選案例與風險後確認，後端重驗草稿版本，才在本機回放建立持倉。

確認前若推進回放、改變持倉或完成其他操作，原草稿便失效，需要重新核對。相同確認識別碼重送回傳既有結果，避免重複建立訂單。取消草稿只取消待確認意圖，不是券商撤單；回放成交也不代表取得券商成交回報。

### 加倉與平倉

已有同向持倉時，新草稿標記為加倉，顯示新增前後總手數、更新後同向均價及整組價格情境損益。提示需提醒「均價改善不代表風險降低」。反向或混合部位另外標示，不能把本機逐筆部位模型當作券商淨額模式。

平倉從持倉列操作並要求使用者確認；查無進場案例時仍可退出部位。回放依 BUY 的 BID、SELL 的 ASK 計算退出損益，更新餘額與歷史。當 K 棒觸及停損或停利時，依明示的模擬規則處理；同棒同時觸及兩者採停損優先，跳空穿越停損採較不利開盤價。這些是回放假設，並非已重建真實逐筆成交。

## 七 風險試算方法與例子

平台把新增訂單風險與整體部位風險分開呈現。以下假設同向 BUY 部位、美元計價、每手 100 盎司。這是初版回放規格，未據此認定任何券商或原交易員合約規格。佣金、隔夜費、保證金與強制平倉未納入，成交模型採固定 0.30 美元價差。

:::equation average
同向平均進場價等於各筆進場價乘手數的加總，再除以同向總手數。
:::

:::equation pnl
多單情境損益等於各筆情境賣出價減進場價，乘手數及每手盎司數後加總；空單價差方向相反。
:::

例如原有 0.10 手 BUY，進場價為 3,000.30；目前 BID 為 2,990.00、ASK 為 2,990.30。若再買入 0.10 手，總部位成為 0.20 手，同向平均進場價為 2,995.30。平均價雖下降，但如果之後 BID 再下跌 10 美元至 2,980.00，原單損失 203 美元，新單損失 103 美元，合計情境損失為 306 美元。

| 情境 | 未加倉的原單 | 新增 0.10 手 | 加倉後合計 |
|---|---|---|---|
| 目前 BID 2,990.00 | 損失 103 美元 | 損失 3 美元 | 損失 106 美元 |
| BID 下跌 5 至 2,985.00 | 損失 153 美元 | 損失 53 美元 | 損失 206 美元 |
| BID 下跌 10 至 2,980.00 | 損失 203 美元 | 損失 103 美元 | 損失 306 美元 |
| BID 下跌 25 至 2,965.00 | 損失 353 美元 | 損失 253 美元 | 損失 606 美元 |

以上是指定價格下的試算，不是最大損失估計。若沒有停損，畫面顯示未設定停損，也不提供計畫風險報酬比。若新單進場 2,990.30、停損 2,980.30、停利 3,010.30，則新增單的價差停損金額為 100 美元，計畫風險報酬比為 2.00。此金額只針對新增單；既有單未設定停損時，不能把它當作整組損失上限。

:::equation stop
新增單停損金額等於進場價與停損價的距離，乘新增手數及每手盎司數。
:::

:::equation rr
計畫風險報酬比等於停利價與進場價的距離，除以進場價與停損價的距離。
:::

系統以字串建立 Decimal，例如 Decimal("0.10")，不先轉成浮點數再建立財務值。顯示金額四捨五入到小數二位，計算中保留原精度。未來若加入其他商品、合約或帳戶幣別，須先取得每手規格、最小跳動、報價幣別及換匯方式，再重算情境，不能沿用黃金展示假設。

## 八 第一版實作狀態與驗收邊界

目前建立的可運行核心以本機回放為主。後端測試涵蓋無停損處理、手數與方向檢查、草稿失效、防重送、平倉損益、成熟案例與案例排序不使用盈虧等情境。測試通過代表所測邏輯符合預期，不代表交易績效、使用者成效或外部服務已驗證。

| 範圍 | 第一版狀態 | 驗收或尚缺條件 |
|---|---|---|
| 歷史回放與部位操作 | 已建立本機流程 | 核對來源標示、收棒界線、開倉與平倉 |
| 案例及價格情境試算 | 已建立透明條件檢索與 Decimal 計算 | 人工核對案例、公式與資料限制 |
| 中文助手 | 本地規則解析可運行 | 核對草稿與表單一致，無自動確認 |
| 外部 LLM | 可選配置介面 | 尚未使用實際金鑰測試回應與摘要內容 |
| 券商模擬 API | 未連線並拒絕操作 | 券商資格、應用審核、商品規格與真實回報 |
| 盤面相似度及 ML | 未啟用或未訓練 | 時區、資料品質、評估設計及另行核准 |

本機回放預設使用合成行情與案例，以便公開程式可獨立啟動；私人案例及既有行情可在本機匯入。合成結果不代表原交易員績效。交付不包含完成使用者研究、勝率提升、因果解釋或完整模仿策略的宣稱。

券商串接候選可考慮 cTrader Open API，其官方文件提供模擬帳戶及 OAuth 帳戶授權流程 [1][2]。是否適用本團隊，仍需逐一確認券商、地區、黃金商品與帳戶資格。MetaTrader 5 的 Python 整合提供終端互通方式 [3]，可作單一展示帳戶候選，但也需要終端、帳戶及事件同步驗證。此處為後續技術選擇依據，並未選定或完成連線。

## 九 八週實作與驗收路線

五人團隊依資料、檢索、後端風險、前端與整合測試分工，工作以每週整合為主。已建立的初版核心可縮短起步時間，後續仍要以可觀察成果驗收。券商連線資格若未完成，須保留完整本機回放展示，並將 API 串接列為獨立未完成項目。

| 週次 | 主要工作 | 可檢查的成果 |
|---|---|---|
| 第 1 週 | 確認資料契約與來源範圍，核對分群 | 可重跑稽核、人工核對樣本與限制清單 |
| 第 2 週 | 完成回放行情、案例成熟界線與資料匯入 | 不顯示未來 K 棒，來源與時間可辨識 |
| 第 3 週 | 整合首筆與加倉檢索 | 相同查詢可重現，盈虧不影響相似度 |
| 第 4 週 | 整合風險試算與草稿確認 | 例子重算一致，舊草稿拒絕，重送不重複 |
| 第 5 週 | 完整券商式介面與中文助手 | 表單及對話共用草稿，鍵盤可操作 |
| 第 6 週 | 條件許可時測試單一券商模擬帳戶 | 下單、拒單、平倉及斷線與帳戶同步證據 |
| 第 7 週 | 多人任務測試與修正 | 記錄正確率、時間、理解及錯誤案例 |
| 第 8 週 | 重現展示、整理報告與交付 | 可啟動程式、示範腳本、限制與驗收紀錄 |

建議任務測試比較一般行情與訂單資訊，以及加入案例與風險提示的介面。讓同一批目標使用者判斷總部位、指定價格損失與是否存在資料缺口，記錄正確率、完成時間及說明理解程度。應平衡任務順序與案例難度，避免只測熟悉過的例子。這是待執行的驗證設計，尚無使用者結果。

## 十 後續擴充階段

### 階段一 券商模擬帳戶與訂單生命週期

前提是選定可用的模擬帳戶與黃金商品，確認合約規格、最小手數、價差、停損距離、事件回報與應用資格。先建立唯讀報價及帳戶同步，再驗證使用者確認後的市價下單與平倉。平台需將送出、接受、成交、部分成交、拒絕及未知狀態分開，不能把 HTTP 成功當作已成交。

完成核心串接後，再加入限價掛單、修改與取消。掛單建立時保留案例與風險檢查，並明示市場變動後的價格及風險可能不同。展示可包含下單、改單、撤單、斷線與恢復；驗證需要對照券商訂單識別碼及帳戶回報，模擬逾時重送、重複事件、部分成交與重啟。缺乏可靠回報時保留未知狀態並停止新操作，避免重複送單。

### 階段二 K 線形狀與盤面相似度

前提是案例時區、帳戶映射及行情覆蓋經過核對，且能辨識每根 K 棒何時完成。功能先加入固定窗口的價格形狀、報酬序列、波動與趨勢條件，讓使用者看到行情相近但操作不同的案例。窗口長度、正規化方式與相似度尺度須固定並保存版本。

展示可把操作條件檢索與加入盤面條件的結果並排，標示匹配原因及缺漏。驗證先人工評估檢索是否符合盤面描述，再依時間切分比較方法；同一候選操作群與跨帳戶同步候選不能跨訓練或測試。所有參數只能在訓練或驗證資料選定，測試期間保持固定。若日後使用 ML，其角色先提供比較證據，不直接生成交易員完整規則。

### 階段三 途中高風險案例與 MAE

前提是持倉期間的行情、手數變化與費用口徑足以重建曝險。MAE 表示持有過程中的最大不利變動，能找出最後獲利但曾承受大幅逆向波動的案例。新增分類需分開「最後實際虧損」與「途中高風險」，避免只以最終盈利判斷操作安全。

展示可在事後回放圖標示最大不利價格與當時可見部位，並比較單筆價格 MAE 與整組金額損失。驗證需抽樣逐根重算，核對加倉前後、價差與行情缺口；不把單筆 MAE 相加當成整組最大損失。MAE 是平倉後標籤，只能用已成熟案例做歷史參考，不能成為當下新訂單的已知特徵。

### 階段四 持倉警示與規則校正

前提是持倉同步與報價足夠穩定，且使用者同意警示條件。先由使用者設定總手數、價格情境損失或資料中斷等條件，程式判斷觸發，助手再解釋原因。沒有連線或可信部位時，警示應說明無法判斷，不顯示已通過風險檢查。

展示包含部位變大、價格逆向及行情中斷後的提醒，並提供確認、稍後提醒與追溯紀錄。驗證警示是否漏報、重複過多、延遲或誤導，記錄觸發前使用的數值與版本。規則可由 LLM 提出文字候選、人工確認後成為版本化設定；不推斷使用者情緒，也不擅自平倉。主動交易權限是另一個需明確評估的範圍。

### 階段五 個人案例與多使用者授權

前提是匯入權利、格式、帳戶及時區可核對。先允許使用者匯入自己的對帳單，完成預覽、品質檢查與確認，再建立個人案例池。共享原交易員案例與個人歷史要分開顯示，不能把不同人的結果混成個人勝率；刪除及重新匯入需保留清楚規則。

再加入登入、獨立回放工作階段、案例隔離與券商模擬帳戶 OAuth。官方 cTrader 授權區分唯讀帳戶權限與交易權限 [2]，產品需清楚說明取得的權限、保存的資料與撤銷方式。展示可讓兩位使用者各自操作模擬帳戶，第三位只做回放；驗證跨使用者資料不可見、權限撤銷後停止操作、token 過期處理及交易紀錄可追溯。初版共享團隊展示帳戶不等於已完成此階段。

### 階段六 商業驗證與部署

前提是核心流程穩定、資料使用權清楚、數值與警示經過任務測試。先與黃金交易使用者、金融社團或教學單位訪談，確認他們是否反覆需要加倉試算、私人案例與提醒，再設計小規模試用。付費方案應依實際價值與服務成本形成，不能先以提高勝率作銷售承諾。

展示成果包含可部署版本、使用指引、資料刪除與權限管理，以及同意下收集的使用紀錄。驗證關注再次使用、核心任務完成率、錯誤回報、支援成本及付費意願；同時檢查資料隔離、備份恢復、事件追溯與負載。真實資金交易仍需另外評估法規、券商責任、故障處理與使用者授權，不由模擬流程驗收自動延伸。

## 十一 預期成果與研究限制

本專題預期交付可運行交易工作台、可重現資料稽核、透明案例檢索、可人工核對的價格風險試算、中文草稿助手與專題文件。展示從首筆、加倉、風險確認到平倉的完整操作，並同時展示無停損、無案例、草稿失效及券商未連線等情境。

資料完整性、時區與單一案例來源仍限制結論。歷史案例不代表所有交易風格，操作條件相似不代表行情成因相同；合成回放不代表券商成交品質。研究成果應以流程正確、資料可追溯與使用者是否理解風險評估，不能以少量展示案例宣稱盈利能力或策略已被模仿。
